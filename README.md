# Delhivery Last-Mile Delay Intelligence Pipeline

Every parcel is booked with a promise: Express in 36 hours, Standard in 60 hours, Economy in 96 hours.
A parcel is **late** when it takes longer than its promise. This repository answers three questions for the
regional operations head, all from one connected set of scripts:

1. **How long will a parcel really take?** (Part B – an estimate of delivery hours.)
2. **Which parcels will be late?** (Part C – a warning flag, raised before the parcel is late.)
3. **Which hubs need which playbook?** (Part D – three groups of hubs, checked against the Tier 1/2/3 labels.)

The data is made up by `generate_data.py` (Delhivery's real records are not used). Money is in Indian Rupees (INR).

**A quick guide to the numbers used below**

| Word | What it means in everyday terms |
|---|---|
| Validation rows | A practice exam. We use it to compare models and to choose settings. |
| Test rows | The final exam. Looked at once, at the very end, so the score is honest. |
| R² | How much of the ups and downs in delivery time the model explains. 1 is perfect. 0 is no better than always guessing the average. |
| RMSE | The typical size of the miss, in hours. Smaller is better. |
| Precision | Of the parcels we flag, how many really were late. |
| Recall | Of the parcels that really were late, how many we flagged. |
| F1 | One score that blends precision and recall. |
| Threshold | The delay probability at which we raise a flag. A parcel is flagged when its probability is at or above it. |

## How to run

Needs Python 3.11 or newer. Run these commands, in this order, from the top folder of a fresh clone:

```bash
pip install -r requirements.txt
python generate_data.py            # prints: 24 1224 48   (writes the three files in data/)
python part_a_clean_eda.py         # cleans the data, writes data/modelling_table.csv and the Part A outputs
python part_b_regression.py        # delivery-hours estimate
python part_c_classification.py    # late-parcel flag and alert threshold
python part_d_segments.py          # hub groups and the tier check
python package_model.py            # saves the final flag model into models/
python predict_delay.py            # turns the 48 new parcels into an action list
```

What each step needs from the ones before it: Part B and Part C read `data/modelling_table.csv` (Part A).
`package_model.py` reads `outputs/part_c_final_config.csv` (Part C). `predict_delay.py` reads the files in `models/`
and `outputs/hub_segments.csv` (Part D).

**About the saved model file.** `requirements.txt` pins the exact versions used (pandas 3.0.6, numpy 2.5.4,
scikit-learn 1.9.1, joblib 1.6.0, on Python 3.12.3). A saved model file (a "pickle") can only be opened safely by the
scikit-learn version that wrote it. So `models/delay_model.pkl` is **regenerated by running `python package_model.py`**.
The committed pickle loads reliably only on the pinned scikit-learn version. If your installed versions differ, run
`package_model.py` again instead of loading the committed pickle. `predict_delay.py` prints this advice if the file cannot be loaded.

Every random step uses `random_state=42`. A full re-run on a clean copy gave byte-for-byte identical CSV files
and an identical pickle, and two runs of `predict_delay.py` give identical output.

**Where things are**

```
generate_data.py           the provided data script, unchanged
src/shipment_prep.py       shared lists + clean_shipments() + build_features(), used by every script
part_a … part_d_*.py       one script per part;  package_model.py, predict_delay.py  finish the build
data/                      the three generated files + modelling_table.csv
models/                    delay_model.pkl, delay_threshold.csv, feature_order.csv, impute_values.csv
outputs/                   every result as CSV
```

## Data findings

**What cleaning did** (all counted by code in `outputs/part_a_checks.csv`): the raw file had 1224 rows; 24 were exact
copies and were removed, leaving 1200 parcels. Five parcels had a weight of 999 kg (a scanner fault; the network
accepts at most 40 kg) and were treated as missing. Gaps were filled with the middle value (median) of the column:
distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50. The service type was written 12 different ways
("EXPRESS", " express ", …) and is now just 3. After cleaning, there are 0 missing values in the model columns.
278 parcels were late, a delay rate of 0.2317.

**(i) Express is late most often.** Express parcels were late at a rate of 0.4897 (119 of 243). Standard was 0.2056
(132 of 642) and Economy only 0.0857 (27 of 315). Express has the tightest promise: its average delivery took
36.8056 hours against a 36-hour promise.

**(ii) The higher the tier number, the more delays.** Delay rate was 0.04 for Tier 1 (16 of 400), 0.215 for Tier 2
(86 of 400) and 0.44 for Tier 3 (176 of 400).

**(iii) Longer distance, many more delays.** Delay rate was 0.0219 for 0–200 km (6 of 274), 0.1368 for 201–400 km
(77 of 563), 0.4364 for 401–600 km (120 of 275) and 0.8523 for 601+ km (75 of 88). Beyond 600 km, most parcels are late.

**(iv) The three columns that move most with delivery hours** (ranked by size, ignoring the sign; from
`outputs/part_a_correlations.csv`): `promised_hours` **+0.8372**, `distance_km` **+0.4013** and `n_stops` **+0.3247**.
A plus sign means "bigger value, longer delivery". Fourth place is very close behind: `hub_daily_capacity` at −0.3237
(bigger hubs deliver faster).

**(v) Why declared value was converted to logs.** Before the change, the average declared value (INR 1,533.05) sat far
above the middle value (INR 1,121.50), because a few very expensive parcels pull the average up. After taking the
natural log, the average (7.0277) and the middle value (7.0224) are almost the same, so the column is no longer
dominated by a handful of extreme parcels.

## Model results (regression)

*Question: how many hours will this parcel take?* Inputs are the 17 pinned columns. The data was split into 840 rows for
learning, 180 for validation and 180 for the final test. The scaler (the step that puts all columns on a comparable
scale) learned from the 840 training rows only. On the training rows, the average of every scaled column is 0.0 (the
largest is below 1e-9). On the test rows, the largest column average is 0.2187. That non-zero value shows the test rows
were not used to set the scale (`outputs/part_b_checks.csv`).

**Baseline (always guess the average).** Validation R² was **−0.0212** and the typical miss (RMSE) was 18.8552 hours.
An R² of about zero means this guess explains none of the variation. Every real model must beat this.

**Who won on validation.** Linear regression, with an RMSE of **4.8912 hours** (R² 0.9313). Gradient boosting was
almost tied at 4.9165 hours (R² 0.9306). Random forest scored 5.468 hours and the single decision tree 6.2796 hours.

**Decision-tree depth: too simple versus too memorised** (`outputs/part_b_tree_depth.csv`):

| Depth | Error on learning rows | Error on validation rows |
|---|---|---|
| 1 | 11.6334 | 12.1324 |
| 2 | 9.3687 | 10.4114 |
| 3 | 7.5295 | 8.7033 |
| 4 | 6.0999 | 7.3896 |
| **6** | **4.7114** | **6.2796** (best) |
| 8 | 3.336 | 6.8385 |
| 12 | 1.3613 | 7.4173 |
| unlimited | 0.0 | 7.789 |

- **Too simple (high bias): depths 1, 2 and 3.** The two errors are close together (depth 1: 11.6334 and 12.1324),
  but both are high. The tree is too small to learn the pattern.
- **Memorising (high variance): depths 12 and unlimited.** The learning error falls to 1.3613 and then 0.0, a perfect
  copy of the training parcels, while the validation error climbs to 7.4173 and 7.789. Depth 8 is where this starts
  (3.336 versus 6.8385, worse than depth 6).
- Depth 6 had the lowest validation error and is the depth used for the decision tree.

**Learning rate for gradient boosting** (`outputs/part_b_gb_learning_rate.csv`): 0.01 gave R² 0.7127, 0.1 gave
**0.9306** and 1.0 gave 0.844. At 0.01, each of the 100 small steps corrects too little, so the model is
still far from the answer when it stops (too slow). At 1.0, each step corrects too much, so the model overshoots and
chases noise in the training data (RMSE 7.3701 against 4.9165 at 0.1). 0.1 was best.

**Cross-check and which model to ship.** Cross-validation (five rounds on 1,020 rows, each round holding back
a different fifth) gave a different order from validation: gradient boosting **0.9352** average R² (spread 0.0044)
against linear regression **0.9261** (spread 0.0048). By the brief's rule, the model with the lowest validation error is
the final model, so linear regression was scored once on the test rows: RMSE 4.5235 hours, R² **0.9493**.
**If I had to choose what planners use, I would ship gradient boosting.** On validation the two are separated by
only a few hundredths of an hour, which on 180 parcels is a tie. Cross-validation compares them on more than five times as many parcels,
over five different cuts, and gradient boosting is ahead by more than either model's spread. The data also contain
"special cases" that a straight-line model cannot express, such as Express parcels in the sale window or rain on long
lanes, and a forest-style model picks these up by itself. The test score of 0.9493 belongs to linear regression. I did not score
gradient boosting on the test rows, so it should get one fresh check on newly delivered parcels before it goes live.
Linear regression stays useful as a simple yardstick that anyone can read.

## Model results (classification)

*Question: will this parcel be late?* The split keeps the share of late parcels the same in each part: 195 late
parcels for learning, 42 for validation and 41 for the test. Every table uses the same flagging rule (late when
the probability is at or above the threshold), so the tables agree with each other.

**The "blind" baseline.** A model that says "on time" for every parcel is right 0.7667 of the time on validation
(138 right, 42 wrong). It sounds decent, but it catches 0 of the 42 late parcels (recall 0.0). It is useless for
the one job we need, which is warning us about late parcels. This is why accuracy alone is not enough here.

**Three classifiers against the 0.5 rule** (`outputs/part_c_models.csv`): logistic regression F1 0.8046, decision
tree (depth 6) 0.747, random forest 0.8. All three score accuracy between 0.8833 and 0.9111, well above the blind 0.7667.

**Which columns carry real signal.** The five bookkeeping columns (label batch, scanner build, tape roll,
sticker serial, shelf slot) have nothing to do with delays. Yet together they got **0.2245** of the random forest's
importance (0.046 + 0.0476 + 0.0499 + 0.0436 + 0.0374 in `part_c_feature_scores.csv`), almost a quarter of its credit, because a forest will find accidental patterns in random numbers. The
F-score test (a plain measure of how well one column separates late from on-time) is much clearer. All five fall outside
the top 7, at ranks 8, 12, 14, 16 and 17, and score at most 4.5847. The seven real columns score between 36.7281 and
389.2131: `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`.

**What the "how many columns to keep" table shows** (`outputs/part_c_selectk.csv`): keeping 5 columns scores F1 0.6988
(too few; we lose the rain and sale flags), 7 columns 0.814, 10 columns 0.814, 12 columns 0.8049 and all 17 columns 0.8.
Seven columns is as good as any larger set, and it is simpler, so we use 7.

**Did tuning help?** No. The untuned forest on the same 7 columns scored F1 **0.814** on validation, against 0.775 for the
full grid search (27 combinations) and 0.7848 for the random search (9 combinations). Inside the training data the two searches
looked equally good (accuracy 0.8952 and 0.8905). On a validation set of 180 parcels with only 42 late ones, a single
parcel moves F1 by roughly 0.01 to 0.02, so these small gaps are close to noise. The honest reading: the forest's
default settings were already about as good as it gets here, and tuning on a small validation set cannot reliably find
improvements. The untuned forest was chosen only because it scored highest.

**Choosing the alert threshold** (`outputs/part_c_thresholds.csv`). Rule: missing a late parcel costs more than an
unneeded call, so take the highest threshold that still catches at least 0.80 of the late parcels on validation.

| Threshold | Precision | Recall | What it means |
|---|---|---|---|
| 0.1 | 0.4824 | 0.9762 | catches nearly everything, but more than half the flags are false alarms |
| 0.3 | 0.6964 | 0.9286 | |
| 0.4 | 0.74 | 0.881 | |
| **0.5** | **0.7955** | **0.8333** | **highest threshold that still meets recall of 0.80** |
| 0.6 | 0.8889 | 0.7619 | fewer false alarms, but recall falls below 0.80, so this fails the rule |

**The chosen threshold is 0.5.**

**Final test result** (looked at once, `outputs/part_c_final_test.csv`): precision **0.6889**, recall **0.7561**,
F1 **0.7209**. Of the 41 late parcels, 31 were caught and 10 were missed. 14 parcels were flagged that were not late.
Compared with validation (recall 0.8333, 35 of 42), test recall is lower and **does not reach the 0.80 target**. With
only 41 late parcels, each one is worth about 2.4 points of recall, so the gap is about three parcels' worth. It could be
luck. It could also be that picking the threshold on the validation rows made validation look a little better than
reality. Either way, expect recall of roughly three-quarters, not four-fifths.

## Operations recommendation

**Escalate segment (9 hubs, delay rate 0.46 on average).** These hubs have the longest lanes and the most stops
per route. Delay rate by hub: Guwahati 0.62, Agartala 0.54, Raipur 0.48, Nagpur 0.46, Patna 0.46, Siliguri 0.44,
Bhubaneswar 0.40, Ranchi 0.38, Kochi 0.36. For comparison, the Standard segment (7 hubs) has an average delay rate of 0.0257
and the Watch segment (8 hubs) 0.155 (`outputs/segment_profile.csv`). Parcels flagged at an Escalate hub should go
to the hub manager.

**Four hubs whose tier label is misleading** (`outputs/tier_vs_segment_mismatch.csv`):

- **Kolkata (HUB07), labelled Tier 1, behaves like Watch.** Delay rate 0.14, average lane 304.736 km. Do not give it
  the light Standard playbook.
- **Nagpur (HUB13), labelled Tier 2, behaves like Escalate.** Delay rate 0.46, average lane 473.32 km. Its label hides how
  stretched it is.
- **Kochi (HUB15), labelled Tier 2, behaves like Escalate.** Delay rate 0.36, average lane 466.514 km. Same problem.
- **Dehradun (HUB22), labelled Tier 3, behaves like Watch.** Delay rate 0.2, average lane 316.738 km. It is doing better
  than its label suggests and does not need the heaviest playbook.

What this means: the tier label does not tell us how a hub behaves day to day, so it should not decide which playbook a hub gets.
Use the segment, built from how the hub actually performs, and refresh it regularly (see the production plan).

**Alert threshold and what to expect.** Flag a parcel when its delay probability is **0.5 or higher**. On the test rows,
precision was 0.6889, so about **7 of every 10 flagged parcels are really late**. Recall was 0.7561, so about
**7.6 of every 10 late parcels are caught** (the other 2 or 3 slip through).

**The 48 new parcels** (`outputs/new_shipment_actions.csv`): **8 were flagged**. Of those, **6 need a hub-manager
escalation** (they are at Escalate hubs) and the other 2 get a proactive customer call. The remaining 40 need no action.

**Why three segments and not more.** Operations runs exactly three playbooks, so K = 3 is fixed. The numbers also back it up
(`outputs/part_d_separation.csv`). The gap between "far apart across groups" and "close together inside a group" jumps from
2.894 with two groups to 5.3928 with three. With four groups it rises only to 6.3047 and with five to 6.8866. That ratio
always creeps up as you add groups, so a higher number alone is not a reason to split further. Both larger versions
also create groups too small to run on their own: sizes 8-7-5-4 for K = 4 (one group of 4 hubs) and 8-7-4-3-2 for K = 5
(groups of 4, 3 and 2 hubs). A playbook cannot be built around two or three hubs.

## Production plan

**(a) How the repository covers production readiness**

| Characteristic | Where it lives in this repository |
|---|---|
| Accuracy | One-time test scores in `part_b_metrics.csv` and `part_c_final_test.csv`; threshold chosen from `part_c_thresholds.csv`. |
| Reliability | `predict_delay.py` fills gaps with stored medians, stops with a clear message if a column is still empty, and tells you to rebuild the model if the pickle cannot be loaded. |
| Reproducibility | Fixed `random_state=42`, pinned `requirements.txt`, the data generator, the run order in this README, and `package_model.py` to rebuild the model. |
| Performance (speed) | Nothing is trained when scoring. A parcel goes through one 100-tree forest on 7 columns. |
| Maintainability | One shared `src/shipment_prep.py`, one script per part, and every setting written to a CSV. |
| Consistency | Training and scoring call the same `clean_shipments` and `build_features`; `models/impute_values.csv` and `models/feature_order.csv` fix the fill-in values and column order. |
| Monitorability | `new_shipment_actions.csv` keeps each parcel's probability, flag and action, so the numbers below can be tracked each week. |

**(b) What to watch each week, and when to act**

1. **Delayed share of delivered parcels.** The history shows 0.2317. Investigate if the weekly share is more than 0.08
   away from that for two weeks running (outside about 0.15 to 0.31). Compare sale weeks only with other sale weeks (see c).
2. **Share of parcels flagged.** On the test rows, 45 of 180 parcels were flagged (31 correct and 14 not late), which is one in four.
   Investigate if the weekly flagged share leaves 0.15 to 0.35 for two weeks running.
3. **Recall on parcels whose outcome is now known.** Test recall was 0.7561. Calculate it every four weeks on parcels that
   have since been delivered (at least 40 late ones, so the number is not noise). Retrain if it falls below 0.65.
4. **Share of parcels with a missing distance.** In the history, 36 of 1200 were missing. If more than 0.10 of a week's
   parcels have no distance, something has broken upstream. Fix the feed first.

**(c) Retraining and the September sale**

- **Schedule:** retrain every 4 weeks with the newest delivered parcels, and straight away if any trigger above fires twice.
  On each retrain, re-choose the threshold on fresh validation rows and re-run `part_d_segments.py` so hub segments stay current.
  Keep a final test set that nobody has used for tuning.
- **Sale window (15–28 September, `sale_event_flag`):** delays are expected to be higher in these two weeks, so never judge
  them against ordinary weeks. Compare sale weeks with the same kind of event, meaning the previous sale window, and set the
  flag from the sales calendar before the window starts. After each sale, add its parcels to the training data so the model
  keeps learning what a sale looks like.
- **What data drift would look like:** longer average lanes (the history's middle is 314.95 km), a growing share of Express
  parcels (the tightest promise and the highest delay rate), more stops per route, more parcels with gaps, a hub changing
  how it behaves (its segment changes), or the five bookkeeping columns starting to matter. Any of these means the old
  patterns no longer hold and it is time to retrain.

## Limitations

- **The data is made up.** Real parcels have causes this data does not (traffic, strikes, breakdowns, address problems). The
  clean results here, including the neat hub groups, will be messier in real life.
- **The test set is small.** It holds only 41 late parcels, so test precision (0.6889), recall (0.7561) and F1 (0.7209) could
  easily move by several points on a different sample. Test recall (0.7561) was also below the 0.80 aimed at on validation.
- **The threshold was tuned on a single validation split.** It rests on 42 late parcels. A different split could have given
  0.4 or 0.6. A threshold chosen on one split is also a little optimistic.
- **Choosing the 7 columns happened before the tuning searches.** The column choice was made on all the training rows, then the five
  cross-validation rounds ran on those same rows. The cross-validation accuracies (0.8952 and 0.8905) are therefore slightly
  generous. Validation and test rows were not involved.
- **Hub groups come from only 50 parcels per hub** over a single 90-day period containing one sale window. A hub's delay rate
  from 50 parcels is rough, so hubs close to a group boundary could move between groups with new data.
- **The recommended regression model was not tested.** Gradient boosting is my pick, but the single test score in this
  repository belongs to linear regression (see the regression section).
